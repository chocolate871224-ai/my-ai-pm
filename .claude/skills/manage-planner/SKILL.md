# manage-planner

## What it does

日常的 Planner 操作，拆成幾條**明確的操作流程**。這是一個**引擎**——只講「怎麼操作」；
`log-work`、`check-now` 這些指令（skill）會讀這個引擎來執行。**資料格式**（檔案／資料夾職責、bullet 符號、
日／週／月格式、stream 區段、collections 命名、tracker 格式、例行事項）的**唯一來源是
[`0_Planner/README.md`](../../0_Planner/README.md)**——本 skill 只引用、不重述。

- **回顧**（週回顧 / 月底 / 年度盤點）→ [`review-planner`](../review-planner/SKILL.md)
- **習慣追蹤**（飲料 / 運動 …）→ [`track-habits`](../track-habits/SKILL.md)
- **效率 / 餘裕 / 忙碌 的階段盤點** → [`review-stage`](../review-stage/SKILL.md)
- **Google Calendar 同步** → [`sync-calendar`](../sync-calendar/SKILL.md)

## When to trigger

- 使用者說「盤點今天」/「今天有什麼事」（→ 流程一）
- 使用者回報某任務 完成／順延／卡住（→ 流程二 / 四）
- 使用者提到要新增的任務，有或沒有日期（→ 流程三）
- 使用者問到未來義務（例行事項、已排事件）
- **不是**週/月/年回顧——那是 `review-planner`。

## 操作流程（幾條核心操作順序）— 本 skill 的核心

每條流程是一段**有順序的步驟**，照順序做。步驟碰到的資料格式細節，定義都在 README。

### 前置（任何流程之前）

1. 跑 `bash Skills/manage-planner/scripts/today.sh` 拿今天日期 → 得 `weekly_file`（本週檔）路徑。
   （多日 session 中系統提示的日期可能落後真實日期，**永遠先跑腳本**。）
2. 需要資料格式時看 [`0_Planner/README.md`](../../0_Planner/README.md)，別在這裡重述。

### 流程一 — 盤點（`/check-now` 指令的底層）

1. **取得今天日期**（前置腳本）→ 定位本週檔。
2. **掃描指定範圍**（依使用者說法選一）：
   - **「盤點今天／本日」** → 讀本週檔今天的區段。
   - **「盤點」無時間詞（回頭檢查有沒有漏記）** → 從今天回看，找所有**未確認**項：過去天的 `[ ]`、模糊的 `[o]`、
     沒更新的 `[~]`。**稀疏／空白的天一定要問**（使用者可能只是忘了記，如「6/22（日）有做什麼嗎？」），別默默跳過。
     按日期分組（最舊的先）。
   - **「盤點明天／下週」** → 只在明確要求時，顯示該未來日／區間的計畫項。
3. **依 stream 列出**剩餘項（跳過空區段）；把 `[o]` 事件帶出來讓使用者看到時間。
4. **收尾**：習慣追蹤的補問（飲料／運動）→ 交給 [`track-habits`](../track-habits/SKILL.md)。

### 流程二 — 標記完成（`/log-work` 指令的底層）

使用者回報完成時，**依序更新三層**：

1. **週檔**：在正確的天找到該 stream 的任務行 → 標 `[x]`，**保留所有註記**（`(延2天)`、`(50%)`、突發前綴 `*`／`+`）。
   使用者說「附註 X」→ 行末補 `(X)`。
2. **月檔**：看該項是否對應本月 Goal／Task → 有就更新；若是行事曆事件 → 標 `[x]`。
3. **主題清單（`Collections/`）**：看該項是否屬於某個主題 → 有就更新它。
4. **回報還剩什麼**。

- **未規劃就完成的事**：用對的突發前綴加到今天對應 stream —— `[x] *任務`（殺入）或 `[x] +任務`（衝刺）。

### 流程三 — 新增任務（`/log-work` 指令的底層）

1. **判斷 stream 歸屬**（工作／生活／事業／學習）；含糊就**問一次**並記住。
2. **有日期** → 放進那個日期的檔：
   - **帶時間的事件／會議** → 記為 `[o]`，並**同步到 Google Calendar**（呼叫 [`sync-calendar`](../sync-calendar/SKILL.md)）。
   - **純排程的工作**（有日期、沒固定時間）→ 只放進那天的週檔，**不進 Google Calendar**。
     （使用者給了日期卻沒說時間，主動問一句：這是要進行事曆的定時事件，還是排來做的工作？）
3. **沒有日期** → 加入**今天**的週檔對應 stream。
4. **會議 know-how（排會議時自動帶）**：一場會議是一串連續動作——前一天排「列印資料／（審查型）準備簽到表」、
   當天記重點、會後 1–2 天排「整理會議記錄」存進 `0_Planner/meeting_logs/`（之後可用 `extract-todos` 抽待辦）。

> **排程 ≠ 死線**：任務上的日期＝「排那天做」，**不是那天到期**。只有使用者明說「死線」才當硬死線。
> 盤點時說「排 M/D」，別從日期製造急迫、也別因此重排優先序。

### 流程四 — 回報延遲 / 等外部（pending）

- **延遲**：原行標 `[>] 延 M/D` → 在目標天新增一行註 `從 M/D`。
- **等外部（pending，卡在客服／審核／別人回覆）**：
  1. 原行標 `[>]`，移進**當天的 `### Notes`**，保留「卡在什麼」的原因。
  2. **往後每一天的 Notes 都帶著它**，直到解決——它只搭在 Notes、不是那些天的一般任務行。
  3. 解決 → 標完成、停止帶。使用者判斷不會解決 → 直接拿掉（別讓死掉的 pending 一直留著）。

## 每條流程都要遵守的規則

- **例行操作直接做、不問**（建檔、標完成、遷移、記日誌／tracker、回填例行）——問例行＝消耗使用者的決策力。
  只有**判斷型**（stream 含糊、範圍不清）、**不可逆／對外**、或**只有使用者才有的資訊**才確認。
  相對日期（「明天／下週」）一律轉絕對；任務名太籠統（「處理 XX」）就問交付物。
- **跨檔同步——一次改到所有相關檔**：Goal 狀態 → 月檔＋goals.md；例行項變更 → README＋月檔例行；
  Stream 增刪 → `0_Planner/README.md`＋各檔區段；行事曆事件狀態 → 月檔 Calendar ↔ Google Calendar
  （經 `sync-calendar`；`@gcal:<id>` 只在月檔、週檔是唯讀鏡像）。
- **不要加進 Planner 的東西**：使用者已自動在做、不需提醒的事。**不主動建議任務**——只記使用者回報的。
  被問「有什麼小事可做」時，只從已在清單上／有死線／快被忘的項目挑。
- **回覆風格**：簡短（非多日狀態不用標題分段）；盤點用條列、跨日比較用表格；檔案引用用 markdown 連結；
  永遠以一個具體的下一項收尾（「剩下：…」）。
